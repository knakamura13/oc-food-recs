# oc-food-recs — audit synthesis and roadmap

*Verified against the live Railway Postgres, the running dev server, a scratch Postgres re-ingest harness, the Railway API/CLI, and production (`https://oc-food.up.railway.app`, HTTP 200) on 2026-09-10.*

---

## 1. Where the app actually stands

**The craft is real.** Roughly 145 PRs have produced a genuinely polished explorer, and the polish is structural rather than cosmetic: CLS measures 0.00 in every configuration tested; axe-core across the filter bar, search, list, map and hero returns **zero WCAG 2.1 AA violations**; touch targets are 44px everywhere except one row of pills; the mobile map is a real `<dialog>` with a correct focus trap that disarms on desktop; `prefers-reduced-motion`, `forced-colors` and `prefers-contrast` all have real implementations. `npm run check` is 0 errors across 4,516 files, `npm test` is 221/221, Playwright is 49 passed / 0 failed. URL state round-trips correctly and is unit-tested. The virtualizer keeps the DOM at ~16 rows out of 916. The tricky parts — the measure cache, the Leaflet spiderfy race, the `replaceState` hydration gate — carry comments that show real problems were solved rather than papered over. TTFB is 135 ms and the homepage-shaped aggregate runs in 77 ms against 1,229 rows on 9 of 500 connections; nothing here is a capacity problem.

**The corpus is rare and the ranking model is smarter than it looks.** 2,379 dated, permalinked mentions from 1,174 named Orange County redditors across 73 threads and 14 subreddits, deduped to 1,229 active restaurants, 916 geocoded. **100% of mentions carry both a permalink and a comment date**, and every rendered quote already links back to the exact source comment — that provenance is better than most commercial aggregators. `aggregate_score` already applies a geometric ½ decay per repeat author so one enthusiast cannot manufacture consensus. That is a thoughtful design decision, and it is completely undocumented anywhere a user can see it.

**Three things are worse than the polish suggests, and none of them are UX.**

- **The write surface is open.** SvelteKit runs form actions *before* any `load` (`node_modules/@sveltejs/kit/src/runtime/server/page/index.js:68-77`), and an `Accept: application/json` POST skips loads entirely (`:57-60`). The only `/admin` auth is a `load` (`src/routes/admin/+layout.server.ts:12-28`). I probed all eight admin actions against production with deliberately non-mutating payloads: every one returned HTTP 200 carrying *the action's own validator error* — `mergeRestaurants` → `"Invalid restaurant ids."`, `addBrand` → `"Brand name is required."` — which means the handler executed with no credentials. `mergeRestaurants` is four un-transacted statements ending in `DELETE FROM restaurants` (`src/lib/server/restaurants/admin.ts:57-111`). Meanwhile the same paths return 404 on GET, because `ADMIN_PASSWORD` is unset on Railway — so the owner believes admin doesn't exist in production while its mutations answer everyone.
- **There is no restore point.** `railway postgres pitr status` → `enabled: false, bucketWired: false, isHaCluster: false`. `volumeInstanceBackupScheduleList` → `[]`. There is exactly one snapshot, auto-created by Railway's vuln auto-patch on 2026-08-22, **expiring 2026-09-21**. `data/backups/` is gitignored; its newest file is a 2,291-byte dump of the *E2E fixture database* (2 restaurants), and `db_backup.py restore` opens with `TRUNCATE mentions, restaurants, threads RESTART IDENTITY CASCADE`. The 46 MB of raw thread HTML that could regenerate the corpus is gitignored and lives on one laptop.
- **13.5 MB of verbatim Reddit is in a public GitHub repo.** `tests/fixtures/thread-01.html` (11.3 MB, 328 distinct `u/` handles) and `thread-02.html` (2.2 MB, 151 handles) are committed to `knakamura13/oc-food-recs`, which the GitHub API reports as `"visibility": "public", "license": null`. They are logged-in old.reddit page saves complete with RES body classes. This contradicts the repo's own `.gitignore:34-39`, which documents exactly the right instinct about raw HTML.

**The product ceiling is that it is an excellent archive and a weak decision tool.** Three measurements define it:

- **It does not know where you are.** `Map.svelte:430-448` calls `getCurrentPosition`, draws a blue dot, calls `setView`, and discards the coordinate. `SortKey` is `"score" | "recency" | "name"` (`types.ts:63`); `rg 'haversine|distance' src` returns only an unrelated Fuse knob. Standing at Tustin center, two of the default top twenty are within two miles while **156 mapped restaurants sit within five**.
- **Its numbers overstate.** One 319-point joke comment ("6 year old me? McDonalds 12 year old me? Del Taco…") pays each of six restaurants in full, putting Del Taco, Elephant Bar, Javier's, McDonalds and Selanne Steakhouse at an identical 381 — one click from the default view, under an H1 reading *Best Mom & Pop Restaurants in Orange County*. Separately, **652 of 838 endorsement rows (78%)** attach to a restaurant whose name never appears in the comment.
- **It is slow where it matters.** `/` returns **905,262 bytes with no `content-encoding`**. Cold load on an emulated mid-range phone: FCP ~14 s. Typing three characters into the search box produced keydown durations of **12,128 / 6,992 / 3,248 ms** against Google's 500 ms "poor" threshold.

**Two corrections to circulating claims.** Production is up — the `oc-food-recs-production.up.railway.app` 404 is a stale hostname, and `README.md:10` is the source still advertising it. And the counter-claim that "the Railway edge compresses nothing" is a header artifact; see §2B.

## 2. The core diagnosis

### A. The app cannot survive being unattended

Four independent single points of failure, none of which any UX work touches:

1. **Unauthenticated destructive writes** (above). A scripted loop of ~1,229 `excludeRestaurant` POSTs blanks the site — and because that handler stamps `reviewed_at`, re-running the pipeline will *not* restore it. Fixing the layout `load` alone does not close this: I rebuilt with only `error(401)` in the layout and every POST still executed.
2. **No backup** (above). Every irreversible write in this roadmap currently lands on an unrecoverable database.
3. **A dropped Postgres connection kills the process.** `src/lib/server/db/index.ts:22-25` creates a `pg.Pool` with no `pool.on('error')` listener; node-postgres re-emits idle-client errors on the Pool, and an unhandled `'error'` on an EventEmitter throws. I reproduced it against the live DB: terminate one idle backend and the process exits code 1 with `57P01` at `pg-pool/index.js:62`. Adding the one-line handler made the pool self-heal and the next query succeed 2.4 s later. `railway.toml` sets `restartPolicyMaxRetries = 3` against Railway's default of 10, so the crash budget is three.
4. **No detection.** There is no `src/hooks.server.ts`, so no `handleError`, no structured logging. Worse, because `/` streams, headers commit at 135 ms and a DB failure arrives as a rejected chunk inside an already-sent **HTTP 200** — an uptime monitor pointed at `/` reports green through a total data outage. There is no healthcheck configured on the Railway service either, so a DB-less deploy is promoted to serving traffic. `/api/health` already returns 503 with `no-store` on DB failure and is wired to nothing.

### B. The delivery problem is a Railway toggle, not a rewrite — and my earlier remedy was wrong

The Railway edge **does** compress dynamic SSR responses, but only honors `gzip` and only when `gzip` is reachable first. Matrix against the non-chunked 404 page (8,809 B origin): `br,gzip` → 8,809 B; `br` → 8,809 B; `*` → 8,809 B; `gzip` → 2,009 B; `gzip, deflate, br, zstd` (real Chrome) → 2,009 B. The "edge compresses nothing" refutation used `br,gzip`, the one ordering this edge refuses. Real browsers get compression on every route **except `/`**, which is uncompressed under every header because it goes out `Transfer-Encoding: chunked` with no `content-length` and no `vary`.

`precompress: true` is irrelevant here — `node_modules/@sveltejs/adapter-node/index.js` calls `builder.compress()` on `build/client` and `build/prerendered` only.

**Where I was wrong: un-streaming is not the fix.** Railway CDN caching is a real per-service product, free, off by default, and available on this service — `railway cdn status --service 293e8e7a-…` returns `{"available": true, "enabled": false}`. Railway's docs state that cacheable responses are buffered at the edge "including responses your service sends with chunked transfer encoding, which cache normally," and that the edge serves "Brotli (preferred) or gzip." So enabling the CDN and adding a `s-maxage` compresses `/` *with the streaming intact*. And the 15 OG/Twitter tags don't need un-streaming either: `buildPageTitle` (`page-meta.ts:10-37`) needs no DB at all, and `buildPageDescription`'s unfiltered branch needs three cheap aggregates — resolve a `pageMeta` eagerly, return it un-promised, and hoist the `<svelte:head>` block out of the `{#await}`.

Byte targets, measured against the exact production body: gzip -6 = **169,418 B**, brotli q11 = **113,504 B**. The 113 KB figure is brotli-only and therefore CDN-only; un-streaming alone would buy ~169 KB. Both are large enough that the payload-shrinking work in §6 stays deferred.

One more constraint dissolved: `SITES_BUILD=1 npm run build` **already fails** on clean `main` and has for 34 commits — `parseSearchParams(url.searchParams)` at `+page.server.ts:262` throws `Cannot access url.searchParams on a page with prerendering enabled`, introduced by 545b540 (#106) on 2026-08-12. "Don't break the Sites build" is not a real constraint. (For the record, `setHeaders` would not have broken it anyway; SvelteKit captures cache-control into `state.prerendering.cache` at `respond.js:204-205`.)

### C. The scoring pipeline credits evidence that isn't about the restaurant

Two independent mechanisms, one fix. A comment's full upvote count is paid to *every* restaurant it names, and every reply in a multi-restaurant subtree is written as an endorsement of *all* of them. The predicate needed to fix the second already exists as tested app code — `namesRestaurant()` at `top-comment-snippet.ts:64-75`, with a `WEAK_NAME_WORDS` stoplist already tuned for this corpus. It is trusted for choosing snippets and ignored for choosing what counts.

I ran the fix against the live DB. Dividing by co-mention count alone removes the chains but promotes **Colony Wine Merchant — 225 points, one person, one thread — to #2**. Adding a `voices/(voices+2)` shrink produces:

```
395.5  v=15  El Farolito          128.1  v=21  Tacos Los Chili's
144.9  v= 8  Sababa Falafel       122.4  v=18  Fuoco Pizza
140.5  v=11  Roma D'Italia        107.3  v= 6  Rosine's
135.4  v= 6  Confetti Italian Ice  94.6  v= 5  Los Sanchez
129.4  v= 6  Tony's Little Italy   93.6  v= 5  Habuya Okinawan
```

Zero chains, zero single-voice entries, every one mapped. **That list is the product.** Ship both terms in one commit; neither works alone. That query was run ad hoc and is committed nowhere — item 3 fixes that first, so the numbers are re-runnable.

### D. Every claim the app makes is unexplained, and there is no page that says who made this

`{restaurant.aggregate_score} pts` renders bare — no title, no aria-label, no tooltip. There is no `/about`, no footer, no nav, no contact address. `meta.source_threads` — id, title, url, subreddit, comment_count for all 73 threads — is queried, serialized into every page load, and used only for a `.length`. The one element the codebase calls `.attribution` is `Hero.svelte:26`: *"Built with SvelteKit, hosted on Railway"* with a monetized referral code, while the 1,174 redditors whose words the site republishes get a `u/` handle and nothing else.

Meanwhile: `mention_count` **is** the distinct-contributor count but the card says "mentions" and 803 cards read "1 mentions"; `endorsement_count` is 0 for 875 rows (71%) of dead ink; the one consensus badge is gated on `endorsement_count >= 15` and fires on **exactly one restaurant**; "New since last visit" can only ever return zero for every user forever (I ran the exact predicate: 0 restaurants have a mention after 2026-06-08); and the thread title is the question — "Why doesn't Fullerton have any good pizza?" and "best hidden gem in OC" produce identical-looking cards.

The corpus is a frozen 40-minute snapshot from 2026-06-14 and nothing on the page says so. That is fine — an honest archive is a good product — but only if it says it is one.

## 3. What to build — ranked

### 1. Make the server safe to leave alone
**Effort: hours. Impact: transformative.** *This is #1 because every other item on this list writes to a database that currently has no lock on the door and no restore point.*

**Auth.** New `src/hooks.server.ts` with a `handle` that rejects any pathname equal to `/admin` or starting with `/admin/` before the router dispatches. A hook may return a `Response`; a `load` may not — that is the whole bug. SvelteKit strips `/__data.json` and route-resolution suffixes at `respond.js:116-119`, so the prefix test covers data requests too. When `ADMIN_PASSWORD` is unset, return a hard 404 for GET *and* POST; otherwise compare with `node:crypto` `timingSafeEqual` and return a real `401` with `www-authenticate: Basic realm="admin", charset="UTF-8"`. Keep the layout load as defence in depth but replace its `throw new Response(...)` with `error(401)` — a thrown `Response` is not special-cased in a load (`utils/error.js:41-43` returns 500 for anything that isn't an `HttpError`), which is why even setting `ADMIN_PASSWORD` today produces a 500 with no browser challenge. A verified 60-line implementation plus tests is at `.../scratchpad/authfix/`.

Then fix the test that certified the bypass: `src/lib/server/admin/layout-auth.test.ts:48-54` asserts `rejects.toMatchObject({status: 401})`, and `toMatchObject` duck-types a `Response`'s own `.status` — it passes on the exact path SvelteKit serves as a 500. Assert `isHttpError(err)` and `not.toBeInstanceOf(Response)`, and add a hook-level test that POSTs with `Accept: application/json`, mocks `$lib/server/restaurants/admin`, and asserts the mutation module was never invoked.

**Then keep `ADMIN_PASSWORD` unset in production deliberately.** The hook makes that a hard 404 on every verb, and `dev` short-circuits it (`+layout.server.ts:14`), so `npm run dev` against `DATABASE_PUBLIC_URL` (`zephyr.proxy.rlwy.net:45021`, TCP proxy ACTIVE) gives the full admin UI against production data with zero internet-facing writes. Same capability, one user, no password to rotate. This also defuses a billing trap: `correctRestaurant`'s address branch reaches an unmetered Google Places POST (`geocode/admin.ts:104-160`), and the *only* thing preventing billable calls today is that `GOOGLE_MAPS_API_KEY` is unset — which is exactly the variable you'd set to fix the 313 unmapped rows. Ship the hook before you set that key. Also correct `CONTRIBUTING.md:46` and `.env.example:12-14`, which both currently assert the opposite of the truth.

**Backups.** `railway postgres pitr enable --service 38139fd5-…`, add a `DAILY` volume backup schedule, and `volumeInstanceBackupLock` the 2026-08-22 snapshot so it stops expiring on the 21st. Adopt a real dump as the pre-mutation ritual — I ran and verified this end to end:

```sh
docker run --rm postgres:18 pg_dump --no-owner --no-privileges -Fc -d "$DATABASE_PUBLIC_URL" > ocfr-$(date -u +%Y%m%dT%H%M%SZ).dump
```

302,377 bytes; restored into a fresh `postgres:18` it reproduces 73 threads / 1,239 restaurants / 2,379 mentions / 25 excluded_brands / 1,564 geocode_cache. A Postgres **18** client is required — the server image is `postgres-ssl:18` and a pg_dump 16 client fails. A verified dump from today is at `.../scratchpad/ocfr-prod.dump`; move it somewhere durable. `scripts/db_backup.py` is not a substitute: it covers 3 of 5 tables, omitting `excluded_brands` (25 curated rows) and `geocode_cache` (1,563 paid lookups). Delete `data/backups/db-backup-20260614T051042Z.json` or make `restore` refuse a file whose restaurant count is an order of magnitude below live — right now "restore the newest backup" wipes production down to two restaurants.

**Resilience.** In the same pool literal at `src/lib/server/db/index.ts:22-25`: `pool.on('error', …)` plus `max: 10, idleTimeoutMillis: 30_000, connectionTimeoutMillis: 5_000, statement_timeout: 10_000, query_timeout: 10_000`. The timeouts matter independently — I pointed a pool at a black-holed address and the query never rejected, watchdog still pending at t+65 s, which today renders as `ExplorerSkeleton` shimmering forever with no error and no retry. Add `healthcheckPath = "/api/health"` to `railway.toml`'s `[deploy]` block, and either delete `restartPolicyMaxRetries = 3` to inherit Railway's default of 10 or comment why 3. Put `handleError` in the same `hooks.server.ts` — one structured `console.error` line, generic message to the client. Skip Sentry; point a free-tier external monitor at `/api/health`, never at `/`.

**Move the raw fixtures.** Replace `tests/fixtures/thread-0{1,2}.html` with a ~50 KB synthetic thread — the parser tests key off DOM shape (`t1_`/`t3_` ids), not identity, so invented handles and bodies covering the real edge cases (nested depth, `[deleted]` author, missing permalink, multi-restaurant body, markdown) exercise the same code. Then `git filter-repo --path tests/fixtures/thread-01.html --path tests/fixtures/thread-02.html --invert-paths` and force-push, because history is the actual exposure. The repo drops 13.5 MB with it.

### 2. Delivery — one CDN toggle, one hoisted head block
**Effort: 3-4 hours. Impact: high.**

**The moment:** someone taps an OC Food Recs link from Reddit on cell data, waits for 905 KB before seeing content, then pastes it to a friend and it unfurls as a grey box.

`railway cdn enable --service oc-food-recs`, plus one line in the `/` load: `setHeaders({ 'cache-control': 'public, s-maxage=300, stale-while-revalidate=3600' })` — HTML caching defaults to Auto, which needs a max-age or s-maxage to cache HTML at all. **Keep the `{#await}`.** No preflight blockers: `/` sends no `Set-Cookie` and no `Vary`, the app sets no cookies anywhere, and admin uses Basic Auth, which the edge never caches. Verify:

```sh
curl -sI -H 'Accept-Encoding: gzip, deflate, br, zstd' https://oc-food.up.railway.app/ | rg 'content-encoding|x-cache|age'
```

Twice — you want `x-cache: MISS` then `HIT`, a rising `age`, and `content-encoding: br`. If the chunked-buffering behavior doesn't hold in practice, the fallback is un-streaming, which buys gzip at ~169 KB. Never re-measure with `Accept-Encoding: br,gzip`.

**300, not 3600.** `+layout.server.ts:1-6` documents that adapter-node exists so "/admin edits show up immediately," and item 4 is entirely admin edits. At under 200 requests a week, a 5-minute TTL absorbs a Reddit-link burst just as completely as an hour while costing 12× less staleness. Leave Purge-Cache-on-Deploy at its default, add `railway cdn purge html` to the ingest runbook next to `pipeline:ingest-batch` (purges propagate in ~10 s), and update that comment to say "within 5 minutes, or immediately after a purge."

**OG tags, independently.** Resolve `pageMeta` eagerly in the `/` load and return it un-promised; move the `<svelte:head>` block from `ExplorerApp.svelte:627-646` into `+page.svelte` outside the `{#await}`, plus the `<link rel="canonical">` that `buildCanonicalShareUrl` (`page-meta.ts:79`) is named for and emits nowhere. Then fix the test that is lying: `tests/url-share.spec.ts:142-159` asserts the og tags exist and **passes today**, because Playwright reads the post-hydration head. Re-do it through `(await request.get('/?cuisine=Mexican')).text()`.

While you're in headers: `api/r/[slug].json/+server.ts:45` has no `cache-control`, and `/fonts/*` carries ETag only, so every repeat visit revalidates five faces.

Note the SEO ceiling honestly: awaiting the promise would *not* have produced indexable rows either. `virtualItems` is `$state([])` populated only in an `onMount` effect (`RestaurantList.svelte:161, 176-199, 503`). Crawlable restaurant content needs item 13, not a change to this load.

*Do not* hand-roll a brotli `hooks.server.ts`, wrap `build/handler.js`, or migrate to adapter-static. The first two are what the CDN toggle is for; the third loses per-URL meta at exactly the moment you're fixing per-URL meta, and its evidence was stale anyway.

### 3. Ranking v2 — co-mention split, low-n shrink, a real tiebreak
**Effort: days. Impact: transformative.**

**The moment:** the first screen of a site called "Best Mom & Pop Restaurants" has to not be McDonald's.

**Commit the query before you change it.** Add `scripts/rank_preview.sql` (or a vitest fixture asserting the top 10) so the numbers in §2C are re-runnable by anyone, including you in six months. Everything below is otherwise unreviewable.

In the `ranked_mentions` CTE (`+page.server.ts:69-98`) add `COUNT(DISTINCT restaurant_id) OVER (PARTITION BY comment_id) AS co_mentions`, divide the SUM at `:96` by it, and multiply the restaurant total by `voices/(voices+2.0)` where `voices` is the existing `COUNT(*) FILTER (WHERE author_rank = 1)`. Change the tiebreak at `:158` to `ORDER BY rank_score DESC, mention_count DESC, newest DESC, name ASC` — there are **112 distinct scores across 1,229 rows**, so past roughly rank 100 the list is alphabetical while claiming to be ranked, and v2 still leaves ~400 rows tied.

Client mirror: `weightedAggregates` (`stores.svelte.ts:241-267`) recomputes this when the subreddit or recency filter slices mentions, and it has no `comment_id`. Cheapest safe route is a precomputed `credit: number` (= 1/n) on `ListMention` (`types.ts:21-24`) so the client multiplies instead of re-deriving. Extend the "must match the literal" contract comment at `stores.svelte.ts:231` to name both terms; four tests in `stores.test.ts` pin the current math.

> **Lens disagreement, resolved by measurement.** Split-alone trades a chain problem for a single-stranger problem (Colony Wine Merchant, one person, to #2). Ship both. Also reject the per-comment *geometric* decay a separate finding proposed — simulated, Del Taco keeps 381 at #2 by winning its own tie-break.

### 4. Evidence hygiene — re-scoped, and gated on durability
**Effort: days. Impact: high.** *Hard prerequisite: item 1's dump and PITR. Second prerequisite: the alias table below.*

**The moment:** a skeptic expands the card to audit the score and finds the evidence arguing against it.

I tested the durability question on a scratch Postgres rather than reasoning about it, and the answer changes this item's shape:

- **Merges do not survive a re-ingest.** I ingested a real thread, merged "TK" into "TK Burger" via the exact `mergeRestaurants` code path, then re-ingested the same file: 16 → 15 → **17** restaurants, with `tk` back as a brand-new row and `tk-burger` back to 3 mentions. `mergeRestaurants` deletes the loser and frees its slug; `assign_slugs` then re-mints it, because by construction the pairs worth merging are exactly the pairs `is_match` fails on (`find_duplicate_candidates.py:87` filters to `if rp.is_match(...): continue`).
- **A rename to a *shorter* name forks the row.** "Mario's Butcher Shop" → "Mario's Deli" produced a new `mario-s-butcher-shop-2` carrying both mentions and left the corrected row at zero mentions — invisible, because the page query's `INNER JOIN ranked_mentions` hides zero-mention rows. A rename to a *longer* name survives, via the `length(EXCLUDED.name) > length(restaurants.name)` CASE at `reddit_pipeline.py:2691`. There is no rename UI at all; `rg -i rename src/` returns nothing.
- **`reingest_all_threads.py` destroys everything.** It runs `TRUNCATE mentions, restaurants, threads RESTART IDENTITY CASCADE` *before* ingesting, which makes the carefully-designed `ON CONFLICT`/`reviewed_at` preservation moot. I ran it with four curations in place; 0 of 4 survived, including the McDonald's exclusion. Cost side: 73 files contain **1,518 root comments** = 1,518 sequential local-LLM calls, ~1-3.5 hours, and the loop `return 1`s on the first exception leaving the DB truncated and half-filled.

**So, in order:**

- **Alias table first.** `restaurant_aliases (slug PK, restaurant_id FK, name, source, created_at)`. On merge, write one row per loser. Then change one query — the `existing` fetch at `reddit_pipeline.py:2645-2647` — to `UNION ALL` alias rows projected as the winner's slug/coords. No change to `is_match` or `assign_slugs`. I verified the mechanism: feeding `assign_slugs` the same "TK" entity with that alias row returns `('TK', 'tk-burger')` instead of `('TK', 'tk')`. Combine it in one migration with a `merge_log` capturing the loser's slug, name, coords and moved/deleted mention ids — that single table is the undo record, the replay script, and the alias source. Wrap `admin.ts:76-110` in `db.transaction` while you're there; its sibling `applyRestaurantCorrection` (`geocode/admin.ts:224-255`) already does, so this is an inconsistency, not a house style.
- **Stop truncating.** Re-ingest is already idempotent per thread (upserts on `slug` and `(thread_id, comment_id, restaurant_id)`, plus the orphan sweep at `:2796-2806`). Drop the TRUNCATE; if a from-scratch rebuild is ever wanted, build into a new database and swap `DATABASE_URL`. Guard the name rule too: `CASE WHEN restaurants.reviewed_at IS NOT NULL THEN restaurants.name WHEN length(EXCLUDED.name) > … END`, reusing the flag the schema already documents as "human decided this."
- **Re-scope the duplicate set.** "84 collisions, ~55 merges" is wrong in kind, not just arithmetic. Grouping active restaurants by normalized name gives 84 groups / 175 rows, which split as **9 same-city-or-all-unknown (18 rows)**, **21 different-cities, all geocoded (42 rows)**, and **54 mixed with at least one ungeocoded member (115 rows)**. The different-city bucket is real distinct locations — El Cholo Santa Ana vs La Habra, Taqueria de Anda La Palma vs Santa Ana, Avila's Lake Forest vs Laguna Niguel — and merging them destroys information irreversibly. Several groups are chains that belong in `excluded_brands`, not merged: Del Taco ×3, McDonald's, Baja Fish Tacos ×2. So: chains → registry (reversible, and the mechanism the schema was built for); the 9 same-city groups → merge, after the alias/log/transaction work; the 54 mixed groups → **geocode first**. They're a geocoding problem before they're a duplicate problem, and coordinates will collapse many of them through `is_match` for free. The geocode-aware detector currently surfaces only 11 pairs because it filters on `lat IS NOT NULL` and cannot see 313 of 1,229 rows at all.

## 5. The 12-month version

**The positioning to own: *the shortlist Orange County locals actually vouch for, with the receipt.*** Not a directory of everything ever said — a curated few hundred places where you can see who said it, when, in which thread, and go there.

The browser export is the real blocker and is a separate scope. Either way, pin that model tag first: a floating tag means two runs of the same thread aren't guaranteed to produce the same restaurants, which quietly compounds every durability problem above.

**The one bet that matters: honesty as the differentiator.** This app cannot beat Yelp on coverage, freshness, hours, or photos, and every attempt makes it a worse Yelp. What it has that nothing else does is 1,174 named locals with dated, permalinked receipts, and a scoring model that deliberately refuses to let one enthusiast fake consensus. Every item above that looks like polish — the co-mention split, the `names_restaurant` filter, the "916 of 1,229" denominator, the "last mentioned 2019" tag, the thin-content `noindex`, the truncation on indexed pages, the removal address, the refusal to fabricate an `aggregateRating` — is the same bet: **show the reader exactly how thin or thick the evidence is, and let them decide.** A site that says "1 person, 2019" is more trustworthy than one that says "381 pts," and trustworthy is the only category this project can win. A site with no contact address and no policy is weaker on that exact axis than the `/about` page item 8 already wants to build.

If only one thing ships this year after item 1, ship item 3 with item 4. A fast, beautiful app that ranks McDonald's second is worth less than a slow one that ranks honestly.

## 6. Explicitly not worth doing

**Google Places hours / "Open now".** The only proposal needing an external API, a new table, a monthly refresh job and a recurring cost — for a signal one tap away inside the Maps link. Item 5's "last mentioned" tag is the cheap 80% with zero dependencies. Text mining can't substitute: across 2,354 published mentions there are 6 closure phrases, 5 new-owner, 4 relocation. Hours are the part that turns this into a worse Yelp.

**Dietary and occasion filters.** The corpus is empty: gluten-free and celiac **0**, halal 0-1, kosher 1, kid/family 6-9, date-night 7-13, vegan 15-21. A "Vegan" chip over 15 restaurants renders a near-empty list and falsely implies the other 1,200 places are hostile. Item 12 covers every one of these honestly, showing the matching sentence.

**A public "Something wrong?" reporting form.** New table, unauthenticated POST, rate-limiting, spam handling, a fourth admin queue — permanent moderation load justified by traffic that has not been demonstrated. Its own premise argues against it: the duplicate queue is empty because no *detector* exists, not because users can't write in. The `/about` contact address in item 8 is the half worth keeping, and it's a mailto, not a form.

**Automated permalink re-checking to detect deleted comments.** `reddit.com/robots.txt` is `Disallow: /` for every agent and the Data API now gates access behind manual approval. This is the one durability idea that would newly put the project in breach; removal-by-request is the correct mechanism, not a fallback.

**The composed "ranking-v2" formula** (per-thread p90 × co-mention split × author decay × recency decay × Bayesian confidence × log diversity). Run against the live DB, the headline benefits missed by 2-4× (San Clemente #59→#23, not #6; Brea #244→#129, not #57) and the recency term **actively demotes** the small-subreddit coverage it was sold as lifting: Laguna Niguel #597→#829, Mission Viejo #517→#788, Tustin #453→#661. Six multiplicative terms, two needing per-slice client recomputation, is a standing SQL/TypeScript divergence hazard. Per-thread p90 normalization is a defensible *third* lever if the leaderboard still looks wrong after item 3 — real, just not first.

**Recency decay in the score.** Reorders exactly 3 restaurants at the cost of the small-city demotions above. Rename the "Recent" sort chip to "Newest" instead — 574 of 1,229 restaurants share just five newest-mention days, so the label is the actual defect.

**A hand-rolled brotli `hooks.server.ts`, a wrapped `build/handler.js`, or the adapter-static migration.** The CDN toggle in item 2 is what these were reaching for. Separately, decide the adapter-static branch rather than hedging around it: `SITES_BUILD=1 npm run build` has been broken for 34 commits, so either delete the branch, the devDependency and the stale comment at `+layout.server.ts:1-6`, or restore it behind a `!building` guard and put it in CI. Do not let it keep functioning as an imaginary constraint on other work.

**An error-reporting SaaS (Sentry et al.).** A `handleError` line in `hooks.server.ts` plus a free-tier external monitor on `/api/health` is the whole detection story for a project at this traffic. Monitoring `/` instead would be actively misleading — a streamed DB failure returns HTTP 200.

**A degraded-page path in `+page.server.ts`.** I diffed `src/routes/+error.svelte` against the `{:catch}` block at `+page.svelte:22-28`: same `<h1>Something went wrong</h1>`, the same sentence "The site hit a snag loading data. Try again in a moment.", the same "Back to restaurants" link, and the "working shell" it sits in is a favicon, a `<Toaster>` and a skip link. Building a second one duplicates it verbatim. If you ever do un-stream, take the honest 500 and delete the `{:catch}` block and its ~40 lines of duplicated CSS so the two can't drift.

**Third-party RUM / web-vitals / a CI byte budget.** Field performance monitoring is not the gap — the curl one-liner in item 2 catches the regression that matters, and Chrome has no CrUX data for this page. But that argument does **not** extend to product analytics, and §6 previously conflated the two. Two rejections below rest on "no evidence anyone does X"; with zero instrumentation those are statements about missing data, not about users. Item 8's first-party counter is what makes them falsifiable, and until it ships they should be read as "unmeasured, deferred," not "disproven."

**Sharing the saved list via `&picks=`.** Cheap, correct, preserves the documented privacy rule at `saved-restaurants.svelte.ts:1-7` — and unmeasured. Nobody knows whether anyone reaches the end of the shortlist flow. Revisit once the counter reports on `restaurant saved`.

**"Search this area" map-bounds filtering.** Requires inverting the one-way `ExplorerApp → Map` data flow, plus a bbox URL param, plus reconciling with the mobile `<dialog>`. Unmeasured whether anyone treats the map as a query surface; item 5's radius chip delivers proximity narrowing without the rewrite. Revisit once the counter reports on `map opened`.

**Back-button history (`pushState`).** Real defect — `rg -c 'pushState' src/` returns **zero**, so one reflexive Back exits the app. But there's also no `popstate`/`afterNavigate` listener, so this means wiring the URL back into `appState` without the write effect at `ExplorerApp.svelte:602-623` re-firing. Feedback-loop risk, not a one-line swap. Known debt; revisit after item 13, when `/r/` pages make history meaningful.

**Splitting the dataset into a content-hashed `/data/restaurants.<hash>.json`.** The byte-identity measurement is real (886,704 of 888,943 payload chars shared across filter URLs), but filter changes use `replaceState` only, so the highest-volume scenario in the argument does not exist. For the one case that does — a first-time recipient of a shared link — a 16 KB shell plus a second round trip is strictly worse than one compressed document. Item 2's edge caching keys on the full query string and covers it.

**Columnar payload encoding.** 90 KB brotli vs 113 KB today — 20% for a hand-rolled codec with a decode path in five files. Brotli already collapses the 271 KB of repeated key names. The one variant that measures is deferring `top_comment_snippet` (267 KB, ~30% of the payload, serving 16 visible rows) at 45 KB brotli vs 113 — worth a look *after* item 2 lands, prefetched after first paint, never lazy-loaded on scroll.

**Full multi-value cuisine re-taxonomy of the 148 raw strings.** `CUISINE_MAP` already merges Sushi→Japanese, Ramen→Japanese, Poke→Japanese, KBBQ→Korean, Coffee→Cafe, and `FilterBar.svelte:151-161` builds counts from the normalizer — the "separate chips" complaint is a no-op. The one-line shadowed-key fix and the singleton disclosure in item 7 capture the real value in minutes.

**A pre-mount SSR render path for the virtualized list.** `virtualItems` is `$state([])` populated only inside an `onMount` effect, so un-streaming does **not** produce indexable rows. A dual render path is days inside a 1,899-line component against documented row-measurement fragility, for ~5 KB brotli. Item 13's non-virtualized page is the workable version.

**Re-instancing the DM Sans fonts.** Real waste — `gvar` is 104,520 of 150,224 decompressed bytes against 13 KB of actual outlines, ~296 KB total — but it's a fontTools pipeline plus regenerated assets for ~1.5 s on slow 4G, against ~790 KB from item 2. The `cache-control` fix for `/fonts/*` rides along free.

**A commercial free-tier tile provider.** MapTiler's free plan is 100k requests/month; a real session measured 8 tiles on first paint rising to **49** after five zooms and three pans, so that's ~2,000 sessions — one good Reddit day exhausts a month. The OSMF public servers are the current dependency and their policy is explicit about blocking heavy users without notice, which means a grey empty map on exactly the day item 13 works. The right answer if traffic ever arrives is self-hosted PMTiles, and this app is unusually well-suited: the OC bounding box is already a constant (`reddit_pipeline.py:70-73`), so a z9-z16 extract is one static file at zero marginal cost. Not now — at under 200 requests a week this is a non-issue, and calling it urgent would be dishonest. Link the attribution today (item 11); revisit the hosting the week the traffic shows up.

**Standalone city and cuisine hub pages, standalone sitemap, standalone JSON-LD.** All three are inert until `/r/[slug]` exists. Line items inside item 13, never projects.

**An RSS feed or `/new` page.** `created_at` is a single bulk-load month (2026-06) for all 2,354 mentions and all 1,229 restaurants. There is no ingest-recency signal to feed it, and comment recency is already a shipped sort and filter.

**Desktop map expansion and keyboard-navigable markers.** The ranked list is the primary desktop surface and is fully keyboard-operable; the `role="application"` container does expose zoom and attribution controls, so it's a degraded secondary aid rather than a blocked task. Item 11 removes the 48 px `--map-list-overlap` decoration that puts 3 of 36 markers under the list panel, and stops there.
